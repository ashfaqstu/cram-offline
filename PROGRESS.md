## What Cram is

Open a lecture PDF, ask it a question, get an answer with the slide number —
offline, on a 2020 midrange phone. Then turn the same slides into flashcards.

The submission's argument, in one line: **Arm's own KleidiAI does nothing on
Armv8.2-A, and we measured where the speed actually comes from instead.**

## Decisions made from measurement

| Decision | Why |
|---|---|
| BM25, **not** embeddings | 1–7 ms, no second model, no extra RAM. Lexical overlap is decisive on decks this size. |
| Retrieve many, **send few** | Prefill is ~14 ms/char here. Sending 8 passages would cost half a minute. |
| Char budget floored at **900** | Tuning for speed drove it to ~400, which truncated a 4-item list and the model **invented two of the four Coffman conditions**. |
| Budget split **greedily**, not evenly | An even split truncated the winning passage to make room for one that went unused. |
| LLM **not pinned** to big cores | 6 unpinned threads (10.95) beat 2 pinned big (8.64) |
| Separate prefill/decode thread counts | Opposite optima: 8 and 6 |
| No phase-adaptive affinity | GGML fixes pool affinity at creation; it cannot be changed later |
| Flashcard prompt phrased as a **student's request** | Terse stacked prohibitions made Llama 3.2 1B **refuse outright** as a suspected jailbreak. |
| Prompt examples from an **unrelated subject** | With deadlock examples, the model copied the example answer verbatim into a real card. |
| Topic **list**, not free text | A typed topic is a guess at the deck's wording; a near-miss silently made cards about the wrong slides. |
| Quiz removed | It was flashcards with different wording. Replaced with Practice. |
| No multi-turn chat | Every retained turn is prompt tokens re-read at 14 ms/char. |

## Optimizations, and what is left

| Done | Effect |
|---|---|
| Retrieve many, send few (BM25 1–7 ms, 1–2 passages) | 34.5 s → ~11 s first word |
| Greedy budget allocation | stopped truncating the winning passage |
| Device calibration at startup | budget sized to the phone, not to ours |
| Separate prefill/decode thread counts (8 / 6) | avoids the 58% decode cliff |
| Q4_0 + GGML aarch64 repack | +15% prefill over Q4_K_M |
| **KV prefix cache** | 14.8 s → 12.6 s (~15%) by not re-reading the system prompt |
| Greedy decoding | same question, same answer |

**Remaining, in rough value order — none started:**

1. **Trim the system prompt itself.** It is ~100 tokens and now cached, so it costs
   once per session rather than per question — but a shorter one would still cut the
   first answer. Low risk, small win.
2. **Cache the passage prefix too** when consecutive questions retrieve the same
   slide. Common while revising one topic; would make follow-ups near-instant. More
   bookkeeping, and the invalidation is where the bugs would be.
3. **Quantize the KV cache** (`q8_0`). Frees memory and can help bandwidth-bound
   decode. Untested here; needs its own A/B before any claim.
4. **A smaller draft model for speculative decoding.** Real speedups on decode, but a
   second model in 6 GB is a memory risk and this is the wrong week to find out.
